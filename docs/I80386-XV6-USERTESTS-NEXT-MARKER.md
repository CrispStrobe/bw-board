# Stock xv6 usertests: next bounded marker

The [stock xv6 prefix receipt](receipts/2026-09-27-xv6-stock-usertests-prefix.json) stopped intentionally when `createdelete ok\n` appeared at 163,992,924 completed guest steps. It did not run the remaining tests and is not a full-suite failure. In pinned MIT xv6-public revision `eeb7b415dbcb12cc362d0783e41c3d1f44066b17`, `main()` calls `linkunlink()` immediately after `createdelete()`; its next completion marker is `linkunlink ok\n`. The program then proceeds to `concreate()` and many further tests.

[`scripts/probe-xv6-usertests-next-marker.py`](../scripts/probe-xv6-usertests-next-marker.py) pins the existing licensed local Bochs BIOS, VGA BIOS, stock xv6 boot disk, filesystem disk and kernel by SHA-256. It checks a clean board revision, the xv6 source revision and test order, then records hashes of the ordinary stock probe and core board sources. `--preflight` performs only these quick checks. Once the shared guest slot is free, `--run` starts a **fresh** 4 MiB stock xv6 boot with `usertests\r`, ordinary CPU execution and a 300,000,000-step ceiling. It stops on `linkunlink ok\n`, or reports that the budget expired first. Rebooting from the original pinned filesystem image is intentional: xv6 creates `usertests.ran`, and a second command in the same filesystem state would decline to run.

Raw serial, local media paths and diagnostic stderr go only to `/mnt/volume1/tmp-astra/xv6-usertests-next-marker-20260928/`. If the old prefix recurs and the next marker is reached or the declared budget expires, the wrapper writes a source/media-bound candidate receipt there. The candidate carries hashes and marker booleans, not the guest transcript or local paths. A missing old prefix, unexpected probe exit or media mismatch fails closed. Reaching `linkunlink ok` establishes only that next test. It does **not** establish complete `usertests` or filesystem integrity beyond that test.

The installed host has QEMU and Bochs executables, but no pinned local stock xv6 oracle transcript for this exact image and test segment was found. An oracle comparison should use a separate copied writable disk and the same image/source hashes; it is not implied by the board marker probe. No QEMU/Bochs run or heavy board run was started while the Windows form census occupied the VPS.
