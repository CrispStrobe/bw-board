## Firmware-only and circuit use

```js
import {createDebugTarget} from 'bw-board/debug-target-factory';

const {target, adapter, refusals} = await createDebugTarget('labwired', {
  wasm,
  firmware: xtensaElfBytes,
  labwiredBoardId: 'esp32-4848s040'
});
adapter.onSerial(byte => appendSerialByte(byte));
target.run();
target.runFor(1_000_000);
const frame = target.video();
```

`firmware` is a nonempty `Uint8Array`. The addressed path requires an ELF32
little-endian Xtensa executable with complete load segments and an executable
entry point. The adapter copies the bytes before creating the machine; reset
uses the private copy. A caller changing its original buffer cannot change a
later boot.

UF2 is explicitly refused here. The package's existing UF2 converter reads a
Cortex-M reset vector and emits an ARM ELF; it is not an Xtensa loader. An
unaddressed raw application `.bin` is also refused.

The existing explicit merged-flash profile can be composed with the trusted
board selector:

```js
const {target, adapter} = await createDebugTarget('labwired', {
  wasm,
  firmware: mergedFlashBytes,
  labwiredBoardId: 'esp32-4848s040',
  firmwareBoot: {
    kind: 'esp32s3-merged-flash',
    irom: admittedIrom,
    drom: admittedDrom,
    console: 'uart0',
    partitionTableOffset: 0x8000
  }
});
```

The host must admit both ROMs by exact size and SHA-256 using
`ESP32S3_FLASH_BOOT_ROMS` before the factory call. All existing merged-flash
validation, copied inputs, partition-derived application offsets and console
selection remain in force; see [ESP32S3-FIRMWARE-BOOT.md](ESP32S3-FIRMWARE-BOOT.md).
The factory validates an image layout, not the correctness or compatibility of
an arbitrary application.

For external H1 components, pass `board` and optionally `mcuId` in either
example. `board` must be the actual `Board` with its parts, nets and electrical
interface. `mcuId` selects an existing `esp32_4848s040` part. Without it, there
must be exactly one such part. The selected part must expose exactly the eight
H1 terminals below. A generic `mcu` fallback is refused. Another controller
sharing these bare GPIO terminal names is refused because the current Board
pin interface does not address a particular controller instance.

`adapter.labwiredBoard` provides frozen identity metadata: `id`, `partKind`,
catalog `sourceCommit`, selected `mcuId`, `displays` and circuit `refusals`.
Firmware-only mode has no H1 pin bindings. Circuit mode retains the canonical
internal display/touch assembly and derives optional external bindings from
the selected part's actual nets.

Use the factory options above for this profile. The lower-level bridge retains
its trusted board identity when it returns derived options; copying those raw
chip/YAML fragments into an adapter is refused rather than dropping into the
generic electrical path.

## H1 connector and electrical scope

The modeled connector is the eight-pin header on the back of the board. The
left and right columns below follow the connector reference from top to
bottom; they are not a generic DevKit pinout.

| Row | Left terminal | Right terminal |
|---|---|---|
| 1 | `gnd` | `gnd2` |
| 2 | `gpio40` | `gpio44` (RXD) |
| 3 | `gpio2` | `gpio43` (TXD) |
| 4 | `gpio1` | `5v` |

GPIO logic is 3.3 V; `5v` is the Board model's separate 5 V supply terminal.
Like the existing board-kind models, it provides a convenience supply fallback
for the circuit. This does not model the regulator or make external supply
voltage drive the engine's reset/power state. Internal LCD, touch, flash and PSRAM signals are not external circuit
terminals. The connector reference is retained by the companion hardware lane
from the [ESPHome Guition board documentation](https://devices.esphome.io/devices/guition-esp32-s3-4848s040/).

The adapter reads only the qualified GPIO OUT/ENABLE, per-pin PAD_DRIVER,
output-matrix and IO_MUX registers for these five pads, and checks the engine's
`pin_routing` result against them. GPIO40/43/44 use bank 1. Direction, pull and
open-drain latch changes are detected even when no logic edge occurs.

GPIO40/43/44 reset in IO_MUX function 0 (MTDO, U0TXD and U0RXD); that is not
GPIO. Their circuit coupling starts suspended, with no GPIO output or injected
external level, while the guest is allowed to boot. Coupling is admitted only
after firmware selects function 1. GPIO1/2 permit their documented GPIO
functions 0 or 1. A later peripheral remux isolates the Board contribution and
releases its former engine input. `target.diagnostics().boardElectrical`
reports `pending`, `ready` or `refused`, plus the connected pad's function and
reason. Pending is explicit absent electrical support for that route, not a
claim that the physical peripheral pad floats.

Ordinary digital input, push-pull output, input pulls and non-inverted GPIO
open-drain output use the shared Board electrical model. An open-drain high
latch means release: an external load may keep the actual wire low. The
adapter distinguishes that latch from pad readback, so it does not turn an
externally low released wire into a fabricated driven-low output. Shared Board
pull and output resistances are model parameters, not measured S040 values.

Electrical coupling is deliberately bounded:

- Only physically connected H1 input or released open-drain nets receive the
  Board solver's boolean level. Unwired pads receive no synthetic board input,
  preserving the engine's own unconnected-pad behavior. A one-terminal net or
  duplicate references to that same terminal do not count as an external wire.
- The dedicated `set_gpio_external(peripheral, pin, level)` interface accepts
  boolean high/low and `null` for actual external release. There are no
  synthetic `board_io` buttons: those would eagerly drive a default input
  during construction. Input-to-output transitions, remux and target detach
  release any prior hold. A backend that cannot release is refused before
  circuit attachment; a release failure halts execution until reset. Failed
  construction isolates every previously seated output. Detachment attempts
  every release even if one fails, removes the old Board binding, and reports
  the error; destruction still clears its listeners and breakpoints.
- The bridge updates solved levels at pump boundaries. This establishes
  digital drive/release coupling, not continuous analog behavior or sub-pump
  pulse timing.
- A connected pad whose output-matrix selector is not plain GPIO (`256`) is
  refused, including input mode: peripheral input routing is not independently
  qualified by this bridge. Output or output-enable inversion is also refused.
- Disabled input buffers on connected inputs/open-drain pads, simultaneous
  pull-up and pull-down, and open-drain with pull-down are refused.
- ADC/analog-source bindings, high-speed peripheral waveforms, UART electrical
  drive, native USB arbitration and bank-1 interrupt delivery are outside this
  bridge's claim. The RXD/TXD connector names do not qualify UART transmission.

The general engine `read_memory` performs bus reads and can have side effects.
The small GPIO configuration register set used here has side-effect-free read
implementations in the qualified supplier. It is not a general peripheral
snapshot or restore API.

## Display projection

The internal component is `display` of type `st7701-rgb`. `target.video()`
returns `null` until the engine reports at least one actual complete DMA frame.
It accepts only the complete 480 by 480 `rgb565_be` artifact and decodes those
bytes to RGBA; it does not synthesize a demo image or fill missing pixels.

```js
{
  width: 480,
  height: 480,
  rgba: Uint8ClampedArray, // 480 * 480 * 4 decoded channels
  frame: Number,          // host frame serial
  signal: Boolean,
  panel: {
    displayOn: Boolean,
    sleeping: Boolean,
    backlightOn: Boolean,
    powered: Boolean,
    framesReceived: Number
  }
}
```

`signal` is true only when the panel is powered, display enabled, awake and
backlight enabled. Off/sleep/backlight state participates in cache invalidation
even if pixel generation did not change. Successful reset or snapshot restore
discards cached pixels so a reused generation cannot display an old session's
frame. Exposing this invalidation does not claim that the S3 engine supports
full-machine snapshots.

The circuit UI binds this frame only to the explicitly selected part id
(`esp32S040PartId`). The engine does not broadcast a frame to every similar
part. Other controllers and unrelated display targets keep their existing
behavior.

## Typed touch input

The internal touch component is `touch` of type `gt911`. The typed API exposes
three channels: integer `x` and `y` from 0 through 479, and `pressed` equal to
0 or 1. Every transaction is validated before the backend receives it:

```js
target.setInputs([
  {component: 'touch', channel: 'x', value: 123},
  {component: 'touch', channel: 'y', value: 456},
  {component: 'touch', channel: 'pressed', value: 1}
]);
target.setInputs([
  {component: 'touch', channel: 'x', value: 321},
  {component: 'touch', channel: 'y', value: 47}
]);
target.setInputs([{component: 'touch', channel: 'pressed', value: 0}]);
```

Press requires both coordinates earlier in the same transaction. `pressed`
must be last, and no channel may repeat. Unknown component ids, omitted touch
identity, fractional or out-of-range values and circuit GPIO writes are
refused. The API uses the engine's atomic `set_inputs`; it does not partially
apply a batch by falling back to separate setters.

The GUI uses one stable `onEsp32S040Input` callback per target session and
releases its captured touch on pointer cancel, target replacement, panel-off
or unmount. `target.detach()` refuses later input from a stale UI callback.
It also releases the old session's H1 inputs and isolates its circuit outputs.
Reset creates a new engine instance, so old GT911 reports do not survive it.

## Qualification boundary

Focused source controls exercise exact selection and refusal, real circuit
topology, voltage separation, bank-1 register reads, copied reset inputs,
display state/cache invalidation and atomic typed-input validation. These
controls use a configuration double and do not establish emulated execution.

The separate real-engine proof must admit the exact release and the
supplier-owned source fixture by length and SHA-256 before importing executable
glue. The fixture bit-bangs the panel's serial initialization, programs actual
LCD/GDMA registers, transfers a full RGB565 image, polls the GT911 by I2C and
redraws in response to host touch. The adapter test must observe that guest
output through this public factory. H1 register-driven controls exercise the
real engine and Board together; they remain distinct from the guest's own
instruction-driven panel/touch proof.

A second retained-input case composes the S040 selector with merged-flash
boot. It requires the unchanged M1 Arduino `SMOKE_OK` artifact to print its
actual UART0 marker before and after reset, while the panel remains pending
because that smoke image does not initialize RGB. Its original incomplete
exact-sketch/toolchain provenance is preserved. This exercises the loading
route and does not establish an S040 Arduino SDK build.

Candidate-engine results are provisional. Production catalog and engine pins
are advanced only after the supplier source and its immutable, independently
repeated build have been qualified. Missing real inputs must fail the dedicated
workflow, not turn into a skipped passing qualification. No physical capture,
compiler coverage, SDK compatibility or hardware flashing result is inferred
from the source fixture.
