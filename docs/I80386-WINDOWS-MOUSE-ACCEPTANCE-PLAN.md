# Windows 3.11 pointer acceptance plan

Source baseline for this audit: bw-board `aafffc245c4c2cc286bb8a226ca5a8efa0962bc2`; Lite's reviewed native-adoption branch `2da17038df970c0a7f2a417a0ac4b32d8deae44b`. This is a test plan, not a new Windows compatibility claim. Microsoft media and screenshots remain in the separately managed private fixture repository.

## Current route and evidence

Lite's [Widgets machine console](https://github.com/CrispStrobe/brickwright-lite/blob/2da17038df970c0a7f2a417a0ac4b32d8deae44b/overlay/scratch-gui/src/components/tw-pseudocode/machine-console.jsx) maps pointer movement to bounded relative `dx,dy`, maps left/right/middle buttons to PS/2 bits, and releases held buttons on blur/lost capture. [GUI mirroring](https://github.com/CrispStrobe/brickwright-lite/blob/2da17038df970c0a7f2a417a0ac4b32d8deae44b/overlay/scratch-gui/src/components/gui/gui.jsx) passes `mouseInFn` to that console. The [debug runner](https://github.com/CrispStrobe/brickwright-lite/blob/2da17038df970c0a7f2a417a0ac4b32d8deae44b/overlay/scratch-gui/src/lib/bw-debug/debug-runner.js) exposes it only when the attached 386 machine can take mouse input.

The board [browser 386 profile](../src/i80386-adapter.js) opts in the auxiliary mouse and advertises it in CMOS equipment byte 14h. `machine.mouseIn()` passes through [the AT machine](../src/i8086-machine.js) to [the 8042](../src/at-8042-a20.js): reporting must be enabled, remote mode and auxiliary-disable must be clear, and three queue slots must be available. Its output status marks auxiliary bytes; the slave PIC receives IRQ12 (PIC2 IRQ4). [The mouse](../src/at-ps2-mouse.js) converts host screen-down Y to PS/2 screen-up Y and emits a three-byte packet. The existing [focused board test](../test/at-ps2-mouse.test.mjs) proves the packet, auxiliary status and IRQ12 edge, but has no Windows guest.

The private `windows311-solitaire-mouse-170m.json` records three accepted events at steps 150,000,000/150,100,000/150,200,000. Its 8042 port trace also records three auxiliary-status/data reads after each event: motion `18 06 aa`, left press `09 00 00`, release `08 00 00` (hex). Thus Windows read the packet bytes, a stronger observation than the host `accepted` return alone, though no application action follows from that fact. The private fixture note reports only a small pointer-region difference in the final Solitaire frame and explicitly says no card move or stock click was shown. Inspection of the saved 640×480 frames shows the large `dx=-250,dy=-170` move pushed the cursor from near the board center to the upper-left screen edge, outside the intended stock card. The nearby keyboard-only `windows311-solitaire-160m.json` ends at a different step, used a different source revision and did not advertise a PS/2 mouse, so its final frame is not a controlled mouse/no-mouse comparison. A separate older Lite GUI receipt reached Program Manager at 640×480, but did not exercise a pointer. Public [enhanced-mode documentation](I80386-WINDOWS-ENHANCED-PROBE.md) accordingly claims game launch/rendering, not pointer interaction.

## Small test first, then guest acceptance

A focused, media-free Lite test is feasible. Render `MachineConsole` with a synthetic 640×480 widget and a collecting `mouseIn` callback. Send pointer move, left/right down/up, lost capture and blur. Assert ordered relative packets, button bit values, saturation, focus, and release; also assert no callback when `mouseIn` is absent. Use [the existing PS/2 pointer unit](https://github.com/CrispStrobe/brickwright-lite/blob/2da17038df970c0a7f2a417a0ac4b32d8deae44b/test/ps2-pointer.test.mjs) as the arithmetic baseline. A built-browser variant can attach a synthetic 386 machine, dispatch real canvas pointer events, and assert `runner.mouseIn` sees them, without shipping Windows media. It would prove host-to-board delivery, not a Windows driver or application response.

For Windows acceptance, run the private immutable image twice at one current board source revision with the **same mouse-enabled CMOS/8042 profile**, same keyboard launch script, same instruction budget and same initial disk bytes. The control has no mouse events; the candidate has a calibrated move, press and release after a captured visible Program Manager or game frame. Capture VGA at just before input, after motion, after press/release, and after a fixed settling interval; retain complete source/input/report hashes privately. Record 8042 auxiliary reads and IRQ12 delivery in the input window. At a minimum, click Program Manager's File menu and require an open menu that is absent in the control, outside the cursor rectangle. A stronger game gate clicks a known Minesweeper covered cell or Solitaire stock and requires a changed tile/card region with no corresponding control change. Check the decoded RGB frame and a named region of interest; a full-frame hash or moved cursor alone is insufficient.

Calibrate movement against the guest cursor rather than assuming one CSS pixel equals one guest pixel: the Widgets canvas uses `object-fit: contain` while the current pointer path sends relative CSS pixel deltas. Record displayed canvas bounds, guest raster size and observed cursor position before choosing the click target. Preserve separate evidence for GUI event delivery, 8042/IRQ12 guest consumption, visible cursor movement, and application action. Only the final application-action gate supports a Solitaire, Minesweeper or Program Manager pointer-interaction claim.

The local private image, scripts and historical board revision are available for a bounded replay, but the static `AT_MOUSE_SCRIPT` harness cannot adjust a click after observing where Windows placed the cursor. A single new 170M static-script run would therefore risk repeating the prior missed click. First derive a calibrated target displacement from a guest frame or add a private checkpoint-time observation/input hook; then run the controlled acceptance replay. The public repository should retain only the media-neutral method and result boundary.
