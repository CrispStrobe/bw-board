# Cold BIOS companion native RAM ownership result

The proposed `scripts/bochs-cpu3-native-cold-owned-ram/` profile passed a local actual full cold BIOS comparison against the unchanged CPU3 callback provider at tested source `7f8c4f07f95e5e1f02618f6868fcbc796b295dad`. Both arms used the same earlier [official CPU3 addon build](https://github.com/CrispStrobe/bw-board/actions/runs/37260140804); the owned arm added a separately built companion N-API module. The [compact result receipt](receipts/i80386-cold-owned-ram-20261007/result.json) records source and addon hashes without local file locations. A dedicated [workflow](../.github/workflows/i80386-native-cold-owned-ram.yml) is available for an exact-head hosted repeat; no hosted result is claimed here.

Both arms completed **316,562 N/Q**, **16,524 resumes** and **16,475 ordered PIO events**. The comparison matched requested full 166-word native state at reset, last return and final inspection, complete final board state, and the SHA-256 of all 16 MiB of final RAM (`af0c07fc87959f6481ab7611967ac40a2c8d3d5fa14beac0979cc99e95913f02`). Both native and provider sessions closed. CPU3 reported the same 91,949 physical reads, 91,958 physical writes, ten execute pages and 167,123 fused memory entries in each arm. Two source tests passed, including concurrent Worker session isolation; workflow lint passed.

This profile copies the initial ordinary RAM and ROM into a C++ session, journals native writes, and reconciles the JS board shadow before clock, PIO and page observers. CPU3 still enters JS for each memory callback, which then calls the companion addon. The result proves this ownership and coherence path for the fixed A20-on free BIOS cold target; it does not remove crossings or measure a speed improvement. It owns no MMIO, paging, DMA or mapping changes, and executes ROM pages only. Direct CPU3-to-owned-RAM access, executed RAM code invalidation and any clock lease require distinct implementation and qualification. Functional JS remains the user-facing baseline.
