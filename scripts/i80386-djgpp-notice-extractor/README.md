# Manufactured DJGPP notice ZIP extractor

This candidate has parsed only synthetic ZIP bytes. It has not read or fetched an actual archive or notice body. It does no filesystem, transport, compiler, guest or GCC-notice acquisition work. All source/handoff/lease/actual-compatibility/complete-notice/legal/compiler/guest flags remain false.

`Extractor().extract(toolchain, djcrx, djdev, djlsr)` consumes one attempt. Four exact builtin immutable bytes must satisfy the four fixed archive extents/hashes before any ZIP offset, structure, CRC or decoder work. Non-DJCRX inputs remain opaque. The internal parser is additionally gated by entered/open/busy/parsing/authenticated-four/unconsumed parser state before struct or decoder work. New, closed and completed direct parser calls refuse without counter work; nested parser/status/extract/close misuse latches refusal, including swallowed reentry at a decoder cut. No caller pins, parser, callback, mutable source container, FD or receipt is accepted. This is a source lifecycle contract, not arbitrary Python reflection or concurrent mutation security.

The conservative ZIP subset uses a fixed terminal 22-byte single-disk EOCD with no archive comment. Central records must exactly cover the stated directory and member count (at most 30,000). Indexed local records must begin at offset zero, remain ordered and contiguous, and end exactly at the central start: no prefixes, overlap, gaps or unindexed local records. Every local header, name, method, flag, CRC and extent joins its central record. Version-needed 10/20, flags zero, stored/deflate, no extras or member comments are supported. ZIP64, encryption, data descriptors, unsupported methods/flags, symlinks/special modes, setid and DOS volume-label attributes refuse. Names are strict printable ASCII at most 240 bytes, with coherent directory/ordinary mode, one directory trailing slash, no absolute/dot/dotdot/NUL/backslash/colon forms. Canonical duplicates and file-ancestor conflicts in either order refuse. These restrictions are a proposed strict source policy; normalized historical inventory does not prove that actual raw DJCRX spelling, attributes or topology comply.

ALL declared ordinary/directory body extents are reserved before any deflate construction: 16MiB per member, 64MiB aggregate, declared expansion ratio at most 1000. These are planning policy caps, not real compatibility or memory/time sufficiency. Compressed input is bounded by the fixed immutable source extent. Stored reads and deflate output chunks are at most 64KiB; each deflate call admits only remaining known extent plus one decoded guard byte, refusing growth immediately. Deflate EOF, unused/trailing compressed bytes, CRC and exact extent are checked for every entry, including empty directories. No full nonselected body cache is kept. Only three exact names copying/copying.dj/copying.lib survive privately after full structure/body closure and exact hash/extent checks; the fixed selected extents total 46,711 bytes. Original exceptions retain identity; partial selected bodies/facts are discarded on failure.

The five-role notice composition also requires two separate pinned GCC byte inputs. The sibling coordinator provides the internal same-call composition; authenticated transport and notice ownership remain unqualified. Three ZIP-derived internal bodies do not establish complete notice coverage, license clearance, archive-to-binary source correspondence or input ownership. `status()` returns copied primitive facts/counts/reasons, never bytes, paths, FDs or adoption tokens. The extractor public API exposes no body-adoption or caller-writer interface. `close()` clears privately retained bodies while preserving finite historical facts; this is not a notice retention or filesystem lease claim.

A 120-second monotonic deadline is cooperative at header/body/decoder boundaries, not a hard process limit. Caller immutable input memory and parser object overhead remain outside operational resource qualification. Twenty manufactured controls patch fixed pins and small fixture bodies, including formfeeds and a 35,147-byte fixture. Both stored and deflated success fixtures pass; negatives cover all-four-before-parser, direct parser admission, ZIP topology, duplicate/ancestor/type/method/extra/comment refusals, CRC/extent/hash, encrypted/descriptor/ZIP64 forms, budgets-before-decompression, decoded guard/tail, swallowed reentry and original decoder-error identity. Earlier review exposed a swallowed CRC reentry calling hash.update before the next poison check. Current source fences CRC, hash construction/update/hexdigest, struct unpacking and reflected decoder attributes immediately before later source work; controls assert zero later hash/CRC/decode/adoption after reentry. This is a finite lifecycle cut, not arbitrary Python object/process security.

Run `python3 -I -B scripts/i80386-djgpp-notice-extractor/controls.py` from the repository root. The [coordinator](../i80386-full-tree-notice-connection/README.md) internally joins the three selected bodies with the two separately pinned GCC bodies. This source-only lane handles free toolchain and notice inputs; it never opens restricted guest media.
