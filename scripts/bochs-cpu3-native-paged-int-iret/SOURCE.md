# Same-ring paged INT30 and IRET source proposal

This separate finite private JS profile extends the independently qualified nonidentity paging layout with a mapped IDT and nonidentity stack. It changes none of the qualified paging, stack or real-mode ROMs, policies, drivers or DSOs. Native INT/IRET admission, preparation, build and execution remain pending. The source plan was reviewed by root before implementation; controls and CPU instructions were pending in the original proposal.

Directory 1000 and table 2000 retain strict 386 two-level 4 KiB paging. Linear code 7000 maps to physical A000; linear stack page D000 maps to physical C000. IDT linear/physical page 3000 is identity mapped. All ten physical pages are copied and reconstructed after each instruction: GDT 0, directory 1000, table 2000, IDT 3000, poisoned original aliases 7000/9000/D000, code A000, prior data page B000, and stack C000. The unused B000 page is retained unchanged; this new program does not claim the previous data-load/store witnesses.

The deterministic 64 KiB ROM installs pre-accessed ring-0 data descriptor 93 and code descriptor 9B, the complete owned code and gate bytes, exact PDE/PTE entries, and three poisoned aliases. It executes LGDT and LIDT with distinct six-byte ROM pointers at offsets 400 and 406. IDTR base is 3000, limit 187 (391 decimal); vector 30 selects bytes `10 70 18 00 00 86 00 00` at 3180: a present DPL0 16-bit interrupt gate, selector 18, handler offset 7010. ROM instruction addresses and store counts are generated from the encoded bytes, rather than copied from the older paging run.

PE, DS=10 and SS=10 are installed before PG. MOV SS is followed immediately by MOV SP,E000. The source oracle retains the actual intermediate returned interrupt/NMI/debug shadows and expects 1/1/0 after MOV SS, then 0/0/0 after MOV SP; it does not claim that these JS shadow fields are exported native inhibit bits. PG is enabled in authenticated identity-mapped ROM after the reset far jump has changed the hidden CS base from FFFF0000 to F0000. A protected far jump reaches nonidentity code 18:7000.

The RAM path is MOV AX,1111 at 7000; INT30 at 7003; handler MOV AX,BEEF at 7010; IRET at 7013; stop before the HLT sentinel at 7005. Boot's EAX upper half 8000 survives both 16-bit MOVs, so the expected final full EAX is 8000BEEF, not zero-extended BEEF. The authentic same-CPL frame consists of FLAGS 0002 at linear DFFE/physical CFFE, CS 0018 at DFFC/CFFC and return IP 7005 at DFFA/CFFA. The handler observes SP DFFA; IRET restores SP E000 and CS:IP 18:7005 with IF clear. No host-created frame or synthetic delivery is used.

The ordinary CPU source remains unchanged. The fixed no-argument factory uses the existing exact-source private Bochs-reset and MOV CR0 model derivative, installing strict386 before the first instruction. It permits only the actual software `_deliver(30,7005,null,{software:true})` from owned instruction 18:7003; hardware interrupt entry, fault delivery, PIO, shutdown, unexpected instruction fetch or store fail closed. The source guard owns every boot/frame byte and seven ordered JS A/D updates. Code and IDT fetch/read entries receive A without D; the mapped stack entry receives A then D during frame preparation. The poisoned physical aliases remain unchanged and unaccessed by the protected program. Full GDT/code/data cache fields, IDTR, CR0/CR3/CR4, complete EAX, stack pointer, all frame bytes and ten entire pages are checked at named cuts.

The JS callback order is explicitly its own. `_prepareStackFrame` prepares translated bytes for `[returnIP,CS,FLAGS]`, then `_commitStackFrame` writes ascending bytes. Its IRET reads IP, CS and FLAGS. Genuine prepared Bochs `exception.cc` SHA `5701d81b89fda61a6c357e63fff653718f6eb6115e3a23d7b23ade15e5d9eb08`, lines 278–330 and 660–714, checks the IDT gate and same privilege and pushes FLAGS, CS and IP. Prepared `iret.cc` SHA `afd03e8eef2e9e90470314c807161ebb2ad44397b29c3f775dec7a866b2dbdae`, lines 100–142 and 156–213, reads FLAGS/CS/IP and restores the same-ring 16-bit SP by six. Equivalent final bytes and architectural effects are required; read/write callback order is not equated across engines.

Prepared `soft_int.cc` SHA `b17cf49a58770b37423d689090a3a23d5774b93a8e7c8af28bb4d76118c01074`, lines 122–155, calls software interrupt delivery without an error word. Prepared `cpu.cc` SHA `16a7b2a3640f2fb3d8df92f8916f8d5bc628e6ed8a7658c07b8db1c101ec80d9`, lines 138–151, places ordinary successful-quanta and native-tick accounting after execute returns. One ordinary JS instruction for INT and IRET is asserted by this proposed source control; native returned accounting and cache/inhibit phases still require a separately admitted first actual guest. Genuine prepared sources were selectively streamed from the sole audited paging build archive; no full tree or second ZIP was extracted. These are Bochs model/source expectations, not hardware corrections or already observed native phases.

The proposed seven cases are five manufactured encoding/ownership/denial checks, one actual private factory/reset/stage check without instructions, and one separately bounded actual fixed JS execution. The last case retains every reset/retired frame, ten copied pages, all stores/A-D updates, actual delivery and physical reads, fourteen named cuts and settled whole-RAM hash outside Git. The instruction bound is 512; a source-derived expected path length uses the current encoded ROM and four RAM instructions, and will not be reported as measured until a genuine capture passes. Clean current/Git identity includes the dynamic CPU source and complete static import/asset closure. These controls had not executed at the original proposal freeze.

A later independent #PF fixture will require identity mapping linear table page 2000, an absent PTE for linear 8000, a real supervisor read fault, actual CR2/error-word/fault IP, ordinary handler PTE repair and legal 386 MOV CR3 reload, error-word discard, IRET and instruction retry. That scope is not included here. No INVLPG, PSE, CR4 extension, task switch, privilege transition, full OS, performance or adoption claim follows from this finite source proposal.
