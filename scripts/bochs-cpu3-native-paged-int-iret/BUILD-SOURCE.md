# Native paged INT30 and IRET build-source proposal

This separate source slice requires a fresh native build for the fixed owned INT30/16-bit IRET ROM. It keeps the qualified paging runtime/provider/DSO frozen as historical `originalPagingProvenance`, alongside original stack, protected-entry, RAM, cold and H4 records. The current profile is `pagedIntIretProfile`; contexts and receipts use `bw.native-paged-int-iret-build-context.v1` and `bw.native-paged-int-iret-build-receipt.v1`. No old addon, including the qualified paging DSO `f3e7406b0b8ce88fcb05be4b99cc0c7a6fab27fa12f1dff071d323ad707a37b7`, can establish INT/IRET admission.

The generated runtime/provider/64 KiB ROM are the source-controlled derivatives from the native policy proposal: runtime `44d6166807419eebc02f6e69f767e22fed21ead738b2a10e71d87791c364b796`, provider `afc02de595449021f64cfa74cb0004ae71028e57596195769563439b5d0f005f`, ROM `b8b3525d4299ba14dc467144fc743a39f1c04d1a7d92ea3b34da6f4ee601cd30`. New roles are `bochs/owned-paged-int-iret-provider.mjs` and `bochs/owned-paged-int-iret-ROM.bin`, with the existing ABI 4/NAPI and authenticated core runtime role. All inherited source inputs plus the nine INT JS/native proposal assets and these seven build assets are explicit current/Git inputs. The final source count remains unmeasured by the new identity until its separately reviewed read-only query.

Each nested admission, materializer and builder authenticates its held module/input hashes, requires exact replacement counts and verifies its full inverse. The materializer first creates the held paging preparation, then finalizes the new profile and writes only its owned new runtime/provider/ROM roles. Configuration authenticates the new fixed ROM and retained VGA bytes. The manual workflow defaults to false and checks out the exact GitHub SHA, fixes Node 22.23.3 and the upstream Bochs revision, and retains full prepared-source/static/failure evidence. It compiles and statically authenticates only when separately dispatched; it cannot load an addon or run a guest.

Six proposed metadata/source cases cover provenance/configuration mutations, exact materializer/builder inverses with definition-only imports, historical profile/schema/DSO refusal, disabled exact-head workflow scope, and complete current/Git/generated identity. Receipts in these controls are explicitly manufactured; the normal wrapper creates a clean owned sparse fixture with read-only object alternates and requires all six nested cases to execute. No control, identity query, materialization, compilation or native CPU execution has run for this build-source draft.

## First execution remains a separate authority

The 512 N/Q values are finite caps, not measured native totals. A fresh static build cannot establish INT/IRET semantic parity. The later driver must retain all 166 native words and compare represented CPU state, actual board state and all ten copied physical pages at reviewed comparable cuts, leaving prefetch/zero-Q phases explicitly unmatched. It must separately attest exact CS/DS/SS descriptor rows, SS valid 1 before the first actual frame store and 7 thereafter, and native MOVSS inhibit versus the separately captured JS shadow fields. These are source-backed expectations, not observations of this unbuilt profile.

Native FLAGS/CS/IP word pushes and the combined stack A/D update have their own successful callback chronology and generations. The private JS source capture measured 41 instructions and seven A/D updates; the native policy expects a combined leaf A/D operation and six updates, without forcing JS callback order or generations onto native execution. Actual counts, phases, fault accounting and correctness remain pending the first separately authorized diagnostic. No operating-system or speed claim follows.
